# Methods and data

## Measurement definitions

| Experiment | Work and timing |
| --- | --- |
| Triad | `A = B + 3C`; two FP64 reads and one write: 24 modeled bytes and two FLOPs per element. Allocation size is the total across all arrays. Ordinary stores: the destination line may be read first (write-allocate), which the counted 24 B ignore. |
| Triad, non-temporal | Same arithmetic and bytes with streaming stores (`vmovntpd`): no read of the destination, so counted equals moved bytes. |
| Read-only | Eight independent AVX-512 load/add accumulators over a private array per thread, first-touched by its owner; each thread loops to the shared deadline with no barrier. 8 B per element. `--per-thread` makes the size per core (hierarchy sweep), otherwise it is the socket total. The kernel reads the clock once per about 4 MiB of passes. The hierarchy campaigns before 2026-10-15 read it after every pass, which understated L1 (91 against 120 B/cycle at 32 KiB, 71 at 16 KiB) and left L2 and memory unchanged; they stay in `data/raw` and in `configs/analysis.json` under `earlier_kernel_campaigns`, used only for that comparison (claim `l1_read_batching`), never pooled with the new ones. |
| AVX-512 FP32/FP64 | Twelve independent FMA accumulators; every FMA counts multiply plus add. Result checksummed against a scalar reference. |
| AVX-512 VNNI | Twelve independent `vpdpbusd` chains (16 lanes × 4 byte-products × 2 operations = 128 per instruction); integer sum compared exactly. |
| AVX-512 BF16 | Twelve independent `vdpbf16ps` chains (16 lanes × 2 products × 2 = 64 per instruction); sum exact in FP32 and compared exactly. |
| Native AMX BF16 / INT8 | Four destination tiles, two operand tiles; `tdpbf16ps` = 16 384, `tdpbssd` = 32 768 operations per instruction. Every output element is checked against its expected value. |
| oneDNN GEMM sweep | `y = x Wᵀ`, `x` of shape M×K, weight N×K; `2MNK` operations per call; modeled bytes = weights + `x` + `y`. Weights are a round-robin pool of identical copies at distinct addresses, at least four times the L3 (Flat) or 16 / 96 GiB (Cache: resident / spilled). Untimed verbose execution proves an AMX implementation; four outputs are checked against references. INT8 runs only if the probe finds a oneDNN path whose verbose log names AMX (`onednn.qlinear_pointwise`, u8×s8). |
| FP64 intensity sweep | Eight independent AVX-512 chains; modeled source read plus destination write. `2NK` FLOPs over `16N` modeled bytes. |
| Copy | `A = B`; one FP64 read and one write: 16 modeled bytes per element, no arithmetic. `copy_nt` writes with `vmovntpd`. This is the traffic shape of the intensity sweep at K = 1, so it is that sweep's ceiling (`report.sweep_ceiling`). Run on both modes on 2026-10-15 (campaign part `copy`, Flat on hbm14, Cache on hbm05): non-temporal copy 610 GB/s on Flat HBM and 228 GB/s on Flat DDR, ordinary copy 601 and 225; the sweep at K = 1 is audited against it. |
| Pointer chase | One randomized cyclic permutation of 64-byte nodes, seed 7, working set 16 KiB–4 GiB (1 GiB in the October idle-latency measurement), one core. A full cycle is traversed before timing. ns/load is elapsed time over dependent loads, including loop and translation overhead. |
| Loaded latency | Part `loadedlat`: the pointer chase (1 GiB, core 0) and a read-only stream of N cores (8 GiB, cores 1…N, N = 1, 4, 14, 28, 55) on the same tier, as two processes in one synchronized timed window (the concurrent-tier mechanism); the idle chase and the stream alone are measured in the same launch. Concurrency is not measured: it is inferred by Little's law, bandwidth × latency ÷ 64 B ÷ cores. Part `flatfar` is the same chase on Flat DDR (16–128 GiB) and Flat HBM (16–48 GiB). |
| Span | One process, 112 threads, 16 GiB. *Interleave*: `numactl --interleave` over both sockets' tier; *first-touch*: `--membind` to both nodes with each thread's pages allocated local. |

**Effective clock and AMX activity.** Every native kernel opens, per OpenMP thread, user-mode `cycles` and the raw event `EXE.AMX_BUSY` (0x02B7) with `perf_event_open`, which works at `perf_event_paranoid=2` because it is per-thread and excludes the kernel. `ghz_effective = Σ cycles / (threads × elapsed)`; `amx_busy_frac = Σ AMX_BUSY / Σ cycles`. Efficiency is reported against the base-clock peak and against the peak at the effective clock.

Five duration-based samples follow warm-up. Native work loops complete whole work blocks, so end times can slightly exceed the planned one-second interval. Actual elapsed time determines the rate. CPU and memory masks follow discovered topology and first touch. Native kernels report the actual OpenMP worker count. The oneDNN path retains numactl restrictions and omits inner GNU OpenMP placement variables.

All participants in a concurrent test finish initialization and warm-up before a readiness barrier. The leader publishes a future start using `CLOCK_MONOTONIC`. Per-sample work and start/end times are retained. Aggregate rate is summed work divided by `max(end) − min(start)`, with shared-window overlap of at least 95%. Adding separately timed participant rates is not permitted.

## Data and selection

`measurements.csv` retains individual samples with portable source paths, campaign IDs, memory socket/locality, implementation, matrix shape, modeled traffic, load counts, timing intervals, compiler evidence, and acceptance reasons. `selection_audit.csv` records source-level admission decisions. INT8 appears only in the September (schema 1.0) campaign, which is archival and rejected as `int8_out_of_scope`; the extended INT8 kernels are in scope.

Compiler metadata and retained disassembly are read from each campaign's system directory. The disassembly check is per loop (`hwbench.disasm`): loops are recovered from backward branches, and a kernel's instruction counts only when an innermost loop holds at least as many copies as the kernel has chains or tiles (8 FMA, 6 `vdpbf16ps`, 8 `vpdpbusd`, 4 AMX tile products, 1 `vmovntpd`). This shows the loop exists and what it holds; it does not prove the timed call reaches it. Failed correctness, invalid timings, worker mismatches, missing ISA evidence, wrong hosts, legacy affinity defects, and dependency-limited sweeps are excluded from thesis statistics. Independent campaigns are never deduplicated; an explicit successful `retry_of` can supersede a source while retaining both records.

The hierarchy and copy campaigns of 2026-10-15 ran Flat on hbm14 and Cache on hbm05, not on the node of the other Cache campaigns (hbm01, occupied by another user's job until the next day); the Cache memory-level points of those two parts therefore carry the Cache-mode variation between campaigns (up to 15% on one node, as much as between nodes; claim `campaign_spread`), and the L1 and L2 points do not depend on it.

`configs/analysis.json` pins a primary memory/sweep campaign per mode, benchmark-specific compute follow-ups, a `supersede` campaign per mode whose longer synchronized windows replace exactly the configurations they re-measured, and the `extended_campaigns` (ISA, bandwidth, hierarchy, GEMM, span, repeat) selected by `hwbench.extended`. Provenance columns `launch_method`, `node`, `memory_mode_verified`, `source_sha256`, `ghz_effective` and `amx_busy_frac` travel with every sample. `summary.csv` summarizes accepted groups without mixing campaign, socket, placement, shape, or implementation. `data/processed/thesis/` contains the exact memory, compute, locality, scaling, knees, concurrent-tier, and theoretical-reference tables used by the notebooks.

Statistics are medians and sample standard deviations of five windows within a run. They describe short-term variation, not confidence intervals over independent machine reboots or allocations. Variation above 5% is retained and flagged. The measured sockets remain separate. No best-socket selection is used.

## Platform conditions

Read from every campaign's platform record, identical in all of them (computed claim `platform_caveats`, shown in notebook 01):

* `intel_pstate=disable` and `mitigations=off` on the kernel command line; frequency is set by `acpi-cpufreq` under the `schedutil` governor, and the highest effective clock any kernel reached is 2.59 GHz against the 3.5 GHz maximum turbo of the data sheet. Efficiency is reported at the measured clock and no turbo claim is made.
* `zone_reclaim_mode = 1`: the kernel reclaims local pages before allocating on another node. Placement is bound explicitly with `numactl`, so this matters mainly for the Cache-mode and spilled working sets.
* Transparent huge pages `always` (defrag `madvise`): large buffers are mapped with huge pages without being asked, which lowers translation cost against a node with the default `madvise`. Latency and bandwidth are measured under this setting.
* SMT is off (one thread per core) and `perf_event_paranoid = 2`, which is why only per-thread user-mode counters are read.

## Rooflines and reference values

`P(I) = min(P_compute, B × I)` and `I_ridge = P_compute / B`. Operations, decimal GB/s and binary GiB are kept distinct. Every pair matches mode and socket scope; campaign ids stay in the tables. Each memory ceiling has one purpose (`report.ACCESS_KERNELS`). Every LLM statement uses the **read-only** ceiling, because weights are only read: the headline roofline, the ridge table (Table 2), the decode bound and the Flat GEMM audit. The FP64 intensity sweep uses the **copy** ceiling (one load and one store per element). The atlas draws the **ERT reference envelope**, the best sustained rate of every kernel including copy (on Flat HBM copy is the fastest, 610 GB/s against 543 for read-only). Cache mode is read at a stated working set: 16 GiB for a resident model, 96 GiB spilled; spilled, a GEMM streams weights faster than the read-only kernel, so a spilled GEMM is audited against Triad, the fastest kernel measured there. Every achieved point is audited against `min(compute, bandwidth × intensity)` for its own tier and path (`roofline.audit_points`); a point above that bound by more than the larger of its own and the ceiling's coefficient of variation is listed in the atlas notebook (section 6) with its ceiling, not hidden. Compute ceilings are measured per execution path at the core count of the workload.

**Decode bound.** The weights of a decoder-only model are read once per generated token, so the read ceiling bounds single-sequence decode independently of the compute path. For Llama-3.1-8B (8.03 billion weights from the architecture in `configs/theory.toml`, 16.1 GB in BF16) the Flat read ceilings give 543 GB/s ÷ 16.1 GB ≈ 34 tokens/s on HBM against 262 GB/s ÷ 16.1 GB ≈ 16 tokens/s on DDR per socket. A decode step (M = 1) has an intensity of about 1 operation per byte, about 200× below the AMX BF16 ridge on HBM (208 op/B). Both numbers are computed claims (`decode_bound`, `decode_far_below_ridge`). They are upper bounds: the KV cache, activations and the per-call cost of the library are not in them.

Theoretical peaks and the model architecture come from `configs/theory.toml`, the single source for them (`analysis.MODEL_SPECS`, used by the architectural-bound check in `validate`, is read from it): per-path operations per cycle (vendor statement or derivation, flagged), 56 cores per socket, and the 1.9 GHz base clock. Because the cores run at 2.0 GHz (AMX) to 2.6 GHz (VNNI) in these kernels, efficiency at the effective clock is the meaningful figure. DDR5-4800 × 8 channels = 307.2 GB/s per socket; the HBM figure is Intel's rounded "up to 1 TB/s" and no bottom-up peak is derived. The firmware (ACPI HMAT) advertises 262 GB/s DDR and 869 GB/s HBM read bandwidth per socket; these appear in the platform record, not as ceilings.

## Comparison with published results

The CPU has two publications with numbers that can be set beside this study's (values in `configs/literature.toml`, table and claims `literature_agreement`, `literature_loaded` and `literature_two_socket` computed in notebook 01). The platform is four NUMA nodes on two sockets, one DDR node and one HBM node per socket, which is the layout McCalpin describes for quadrant clustering; the clustering setting itself is not readable without privileged access, so "same mode" rests on that layout.

| One socket, 56 cores, Flat | Published | This study | This / published |
| --- | --- | --- | --- |
| DDR5 read-only | 237 GB/s | 262 GB/s | 1.11 |
| DDR5 STREAM Triad | 200 GB/s | 235 GB/s | 1.17 |
| HBM read-only | 555 GB/s | 543 GB/s | 0.98 |
| HBM STREAM Triad | 700 GB/s | 554 GB/s (non-temporal 551) | 0.79 |
| HBM over DDR, read-only | 2.3× | 2.07× | 0.90 |
| HBM over DDR, Triad | 3.5× | 2.36× | 0.67 |

Published values: J. D. McCalpin, "Bandwidth Limits in the Intel Xeon Max (Sapphire Rapids with HBM) Processors", IXPUG Workshop at ISC 2023, TACC, 24 May 2023, slides 3–4 ([PDF](https://www.ixpug.org/images/docs/ISC23/McCalpin_SPR_BW_limits_2023-05-24_final.pdf)): Flat mode, quadrant, one socket; DDR5-4800 with one single-rank DIMM per channel. Compiler flags and clock are not stated.

* **Agreement.** HBM read-only is within 2.1% of the published value, so the HBM read ceiling used for every LLM statement is not particular to this node. DDR is 11–17% higher here; the DIMM population of CRESCO8 and the published system are not known to match, so the difference is not attributed.
* **Disagreement, explained (not a hardware difference).** HBM Triad here is 21% below the published STREAM figure. The unmodified `stream.c` on this node reproduces the figure (678–688 GB/s with GCC, 704–711 GB/s with Intel icx and streaming stores, against 700 published), so the node is not slower. The thesis kernel differs from STREAM in three ways that were isolated one at a time on the same node: its initial data (arithmetic patterns) are 12% slower than constant data, its loop (one cache line per iteration) is 6% slower than a four-line unrolled loop, and the thesis reports the median of one-second windows where STREAM reports the best of many short iterations (+9–15%). Software prefetch, huge pages, placement and pointer reloads are not causes. Why the data pattern matters was not measured (RAPL and the uncore clock need root). The thesis Triad (554 GB/s) stays a correct sustained value for its data. The data effect also holds for read-only HBM: the thesis pattern behaves like random data (527 GB/s here), constants and zeros read 575–595 GB/s, so the read ceiling is a high-entropy-data figure and its agreement with the published 555 GB/s does not make it data independent. The published Triad does not exceed McCalpin's read limit (575–590 GB/s): with streaming stores it is about 467 GB/s of reads and 233 GB/s of writes. Evidence, tables and the open questions: [STREAMGAP.md](STREAMGAP.md). The HBM-over-DDR Triad ratio of 2.36 against 3.5 follows from the kernel and data, not from the node. For decode, the read-only ratio is the relevant one.
* **Loaded latency.** The chase beside 55 streaming cores takes 209 ns on HBM (published queue occupancy with all cores streaming: 199 ns, slide 16) and Little's law on this study's rate and latency gives 32.6 outstanding lines per core (published: 31.8). With one streaming core: 143 ns and 37.3 lines against 134 ns and 40.2 (slide 14). The agreement is within 7%, which supports the loaded-latency curve of notebook 02; the concurrency here is inferred from rate and latency, not read from a counter.
* **Different configuration.** I. Z. Reguly, "Comparative evaluation of bandwidth-bound applications on the Intel Xeon CPU MAX Series", arXiv:2309.09084, 2023, section 2 ([abstract](https://arxiv.org/abs/2309.09084)): two sockets, HBM-only mode, SNC4, hyperthreading on, BabelStream Triad 1446 GB/s (1643 GB/s with streaming stores). Flat mode here reaches 1130 GB/s on two sockets (78% and 69%); that comparison mixes memory mode, clustering mode and a different benchmark, and is not a like-for-like check. McCalpin (slide 18) reports that SNC4 raises sustained bandwidth, which is consistent with the direction.

## Uncertainty and conventions

* **Reference socket.** Every headline number is socket 0; socket 1 is shown as a difference (`local_remote_table`) or in the tables that list both sockets. Averaging the two sockets is not used for a headline.
* **Like for like.** A ratio between tiers compares the same kernel on both (HBM over DDR is 2.07× read-only, 2.36× Triad, 2.35× non-temporal Triad); a ceiling may use a different kernel per tier only when it says so.
* **Within a run.** Five one-second samples per configuration; the figures quote the median with the minimum and maximum. The coefficient of variation is computed per *configuration* (benchmark, tier, threads, working set, GEMM shape and batch), never pooled across shapes.
* **Between runs.** Three uncertainties sit next to the sample spread in the decomposition table of notebook 01 (Table 1 of the master notebook quotes only their conservative sum): the range of three back-to-back `repeat` launches; the range of every selected campaign that measured the same configuration on the mode's reference node, launched on different days (`report.campaign_spread`); and the cross-check deviation (`xcheck`: same node for Flat, a second node for Cache), using the quantity's own repeat where one exists and its family's otherwise. The total is the spread plus the largest of the three. Flat campaigns agree to 3% at most; Cache campaigns on one node differ by up to 15% (non-temporal Triad at 8 GiB), as much as the second Cache node does, so no Cache difference is attributed to the node.
* **First window.** In Cache mode the first window of a GEMM on a pool larger than the HBM cache is cold; medians are unaffected (under 3%), minima are not steady-state. On Flat HBM the first window of a 56-core stream is about 7% *fast* (none on DDR, none with 14 cores; claim `hbm_first_window`); Table 1 gives the sustained median without it.
* **Ridge points.** The ridges quoted in the master notebook (Table 2, the decode claims) use the read-only ceiling on every tier; the atlas tables use the ERT envelope and say so. `thesis/knees.csv` is the October export and uses the October Triad bandwidth of its tier (its `bandwidth_kernel` column says so); it is not used for a statement.
